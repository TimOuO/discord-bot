# 冷卻/資源檢查改用 conditional update，依「失敗代價」選「先搶」或「單一原子寫入」兩種手法

原本 `battle`/`dungeon`/`fish`/`gather`/`claimDaily` 都是「先讀 `lastX` 判斷冷卻/是否已簽到、算完獎勵才寫回」，`buyItem`/`sellItemQuantity` 是「先讀金幣/庫存數量、算完才扣」。這中間有空窗：連點兩下按鈕、或語音自動簽到跟手動 `/rpg daily` 幾乎同時觸發，兩個請求都可能通過檢查、都真的寫入一次，繞過冷卻或把金幣扣成負數。

修法是把「檢查」跟「寫入」包進同一個 conditional update，讓資料庫（單一寫入行程的 SQLite）自己做原子判斷，但依「檢查通過後、真正寫入前失敗會損失多少」選了兩種不同手法：

- **先搶再算**（`battle`/`dungeon`/`fish`/`gather`）：一開始就用帶條件的 `updateMany` 把 `lastX` 搶先寫成現在時間，`count === 0` 代表搶輸、還在冷卻；接下來的戰鬥/釣魚/採集邏輯照舊。代價是搶到之後中途出錯，冷卻會被吃掉——但這幾個冷卻只有 30 秒～5 分鐘，重試成本低，可以接受。
- **單一原子寫入**（`claimDaily`）：不能用搶的，一次失敗就是損失一整天的簽到機會。改成把「今天還沒領」的條件（`lastDaily` 是 null 或早於台北時間今天 00:00）跟金幣/經驗/連續天數的所有寫入包在**同一個** conditional update 裡，要嘛整包成立、要嘛整包不動；`count === 0` 才代表已經領過。

`buyItem`/`sellItemQuantity` 用的是同一種「單一原子寫入」手法（金幣/庫存數量的門檻直接寫進 `updateMany` 的 `where`），理由跟 daily 一樣：買賣本來就是「檢查」跟「唯一的寫入」同時發生，沒有「先佔位、之後再確認」這種中間狀態可用。

考慮過統一都用「先搶」以求手法一致，但 daily 簽到的獎勵計算（連續天數、金幣/經驗加成）需要在寫入前就算好完整的資料，搶完再算的話，算失敗一樣會損失當天的簽到，跟原本想避免的問題一樣；而且 daily 一天只觸發一次，不像戰鬥/釣魚可能被連點，用原子寫入不會有效能疑慮，沒有理由為了手法一致犧牲正確性。
