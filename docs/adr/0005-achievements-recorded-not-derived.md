# 成就達成後寫入資料庫，不是每次重新推導

成就的條件全部只看「現在查得到的狀態」——等級、金幣、連續簽到天數、最高強化等級、持有幾件神話裝備、庫存裡的傳說材料數量、目前的職業。既然條件是可推導的，最省事的做法是每次要顯示或計算時重新跑一遍條件，什麼都不用存。

我們選擇**不**這樣做，而是新增 `UserAchievement`，第一次偵測到條件滿足時把 `key` 跟時間寫進去，之後永久有效。

原因是這個遊戲的狀態幾乎每一項都會往下掉：金幣花掉就沒了，強化失敗會退級，裝備可以賣掉，連續簽到斷一天就歸零，職業換掉就不是原來那個。如果成就是即時推導的，「把一件裝備強化到 +10」會在下一次強化失敗退回 +9 的瞬間消失，連帶把它給的攻擊力也收回去。那不叫成就，那叫狀態列。玩家對「成就」這個詞的預期是一次達成、永久留存，而這件事**只能靠記錄**表達。

這是對 [ADR 0001](0001-effective-stats-computed-not-stored.md)「有效屬性即時計算不寫入」的一次明確例外，理由剛好是同一條原則的反面：裝備加成不存，是因為裝備現在在身上就該生效、脫下就該失效，當下狀態**就是**答案；成就要存，是因為當下狀態**不是**答案，答案是歷史。兩者的判準一致——存的東西要是推導不出來的那一部分。

## 代價

- 條件寫錯、閾值調動之後，已經發出去的紀錄不會自動跟著改。閾值調低會讓新玩家更早拿到，但調高**不會**把已經拿到的人收回去（也不該收回去）。真的要撤只能手動刪列。
- 「有沒有達成」跟「有沒有被偵測到」是兩個不同的時間點。偵測是懶惰的（玩家打開 `/rpg profile`、`/rpg inventory`、`/rpg achievements`、`/rpg daily` 時才算一次並補寫），所以條件滿足的那一刻不會馬上有反應，`achievedAt` 記的是**偵測到**的時間，不是真正達成的時間。這是刻意的取捨：另一條路是在每個動作點（戰鬥、強化、採集）都插入偵測，那會把成本加進所有熱路徑，換來的只是時間戳精準一點。

## 考慮過的其他做法

- **每次即時推導、不存**：不用新增資料表、不用遷移，但如上所述表達不出「曾經達成」，而且成就給的能力值會隨狀態漂移，玩家的戰鬥力會無法解釋地上下跳。
- **只存曾經達到的最高水位（最高等級、最高強化、金幣歷史高點……）**：也能表達「曾經」，而且比成就列表更通用。但那是替每一個屬性各開一個新欄位去追蹤，而我們真正想知道的只有十幾個離散的門檻；存水位還得在每個會讓數值上升的地方寫回，散在整個 codebase，跟懶惰偵測的初衷相反。
- **累積計數型成就（打過 100 場、釣過 500 條魚）**：這種本來就非存不可，但那是另一個決定；我們刻意先不做，因為現在沒有任何計數器，加進來等於要在每個動作點寫一次資料庫。條件只用現成的狀態，才能讓偵測完全集中在讀取端。
